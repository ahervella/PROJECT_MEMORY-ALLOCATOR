## Topics discussed

- **`argc`/`argv` in `main`** — `argc` ("argument count") is at least 1 by default because `argv[0]` conventionally holds the program's own invocation name/path. Standard C/C++ behavior inherited from C; see the "Function main()" / command-line arguments sections of Stroustrup's *The C++ Programming Language* or *A Tour of C++*.
- **`.h` vs `.cpp` and `inline`** — `inline` functions must have their definition visible in every translation unit that calls them (ODR relaxation requires identical definitions everywhere), so they belong in headers, not `.cpp` files. See linkage/translation-unit chapters of Stroustrup's *The C++ Programming Language* (4th ed.) or *A Tour of C++*.
- **`.inl` files** — a plain-text idiom (`#include`d at the bottom of a header) for keeping inline/template definitions visible everywhere while keeping the header itself uncluttered. Preprocessor-level only, so no compile-time or runtime performance difference vs. writing the same code directly in the `.h`. Same chapters as above cover translation units/preprocessing.
- **Overloading `operator new`/`operator new[]`** — `operator new` is overloadable like any function, differentiated by parameter list; placement new (`operator new(size_t, void*)`) is a built-in example, and a custom `operator new(size_t, MemoryManager&)` is just another overload, invoked via `new (mgr) T(...)`. IBM tutorial, "Overloading the new and delete Operators."
- **`operator new[]` size parameter** — signature is `void* operator new[](std::size_t size)`, a single total-byte count; the compiler (not the operator) computes `n * sizeof(element)` at the call site before invoking it. Compilers may pad this size further for an "array cookie" (element count) when the element type has a non-trivial destructor, so it can be more than `n * sizeof(element)`. IBM tutorial, Listing 3.
- **Union/struct free-list trick (IBM tutorial, Listing 5)** — wrapping an object's data members in a struct and unioning that struct with a pointer lets a free (unused) pool block reuse its own memory to store the intrusive free-list "next" pointer, at no extra memory cost, since `union` members share storage (size = largest member) rather than adding up like `struct` members do. Covered in Stroustrup's *The C++ Programming Language* (4th ed.), Chapter 8 "Structures, Unions, and Enumerations," §8.3 "Unions" / §8.3.1 "Unions and Classes" — confirmed present via direct read of the book's table of contents. Not found (via text search) in *A Tour of C++*, *Effective Modern C++*, or *Sams Teach Yourself C++ in 24 Hours*.
- **`*` is prefix-only; no postfix dereference** — `*p` dereferences `p`; `p*` is not dereference syntax at all (parsed as an incomplete binary multiplication, since `*` is overloaded between unary-prefix-dereference and binary-multiplication depending on position). `p->m` exists as its own operator (equivalent to `(*p).m`) specifically because `.` binds tighter than prefix `*`, so `*p.m` alone would incorrectly try to dereference `p.m`. Stroustrup, *The C++ Programming Language* (4th ed.), Chapter 8, pointer/member-access section quoted: "When p is a pointer, p->m is equivalent to (∗p).m."
- **`extern` keyword** — declares a variable/function is defined in another translation unit, without allocating storage itself; used to share one global variable's definition across multiple `.cpp` files, and in `extern "C"` to disable C++ name mangling for C interop. Functions have external linkage by default (rarely need explicit `extern`); it matters mainly for variable declarations. See linkage/declaration-vs-definition sections of Stroustrup's *The C++ Programming Language* (4th ed.) or *A Tour of C++*.
- **Translation unit, precisely** — a TU is one source file plus everything pulled in via `#include` (recursively), minus anything stripped by conditional compilation, after macro expansion; it's the preprocessed result, not the raw `.cpp` file. A header is never a TU by itself — only the expanded content inside whichever `.cpp` includes it. The compiler compiles one TU at a time in total isolation (one object file each); the linker later reconciles cross-TU references. Standard's own definition of the term; see the translation/phases-of-compilation material in Stroustrup's *The C++ Programming Language* (4th ed.) or *A Tour of C++*.
- **`struct` vs `class`, and nesting one in the other** — the only real language differences are default access (public for `struct`, private for `class`, for both members and base classes) and that `template<class T>` is valid while `template<struct T>` is not; everything else is convention. Nesting one inside the other creates a scoped nested type (`Outer::Inner`) with no automatic runtime relationship between instances — the nested type's outside visibility follows its access section in Outer, and (since C++11) its member functions get the same access to Outer's private members as any other Outer member would. Stroustrup, *The C++ Programming Language* (4th ed.), class/struct and nested-class sections; *A Tour of C++* for the shorter version.
- **`{}` vs `()` init has nothing to do with struct vs class** — both `struct` and `class` support both forms identically. `{}` (list-init, C++11+) disallows narrowing conversions and prefers an `initializer_list` constructor if present; `()` (direct-init) does normal overload resolution and allows narrowing. Stroustrup, *The C++ Programming Language* (4th ed.), initialization chapter (list-initialization / direct-vs-copy-initialization).
- **Why struct commonly uses `{}` and class commonly uses `()`** — historical, not a rule. Aggregates (typical structs, no user constructors) only ever supported `{}` init until C++20 added parenthesized aggregate init; `()` was the only way to call a constructor before C++11 added `{}` list-init. `{}` on a type with constructors also preferentially binds to an `initializer_list` overload if one exists (e.g. `vector<int> v(10,5)` vs `v{10,5}` differ completely), which is why many style guides still default to `()` for ordinary constructor calls. Stroustrup, *The C++ Programming Language* (4th ed.), initialization/uniform-initialization chapter.
- **`.inl` files vs the `inline` keyword** — the `.inl` file itself does nothing; it's just text `#include`d into a header, identical to typing it there directly. The `inline` **keyword** is what matters: it relaxes the One Definition Rule so the same definition can legally appear in multiple translation units (the load-bearing effect today), and secondarily hints the compiler may substitute the call site (mostly vestigial now — compilers decide this via their own heuristics). A `.cpp` file can't achieve the same result as a `.inl` file not because of the extension (irrelevant to the compiler) but because `.cpp` files are compiled standalone as their own TU by convention/tooling, never `#include`d elsewhere — so a definition placed there only reaches the one TU it's compiled into. Same linkage/translation-unit chapters as the `.h` vs `.cpp` and `inline` entry above.
- **Where `.cpp` vs `.inl` diverge in the pipeline** — not a phase within one compilation run; it's decided by the build system before the pipeline starts, since it invokes the compiler once per `.cpp` file as an independent preprocess→compile→object-file run, and never does this for `.inl`/`.h` files directly. A `.inl` file only enters the pipeline as text pulled in during preprocessing (phase 1) of whichever `.cpp`'s `#include` chain reaches it; by the compilation-proper phase (parsing/semantic analysis/codegen) everything is already flattened into one token stream with no trace of original file boundaries. See the "phases of translation" / preprocessing material in Stroustrup's *The C++ Programming Language* (4th ed.).
- **In-class member function definitions are implicitly `inline`** — not "defined in a header" but specifically "defined inside the class body" (constructors, destructors, any member function) implicitly gets `inline`, no keyword needed. Declaring in-class but defining out-of-class (`void Foo::bar() {...}`) does NOT get implicit inline even if that definition is physically in the same header — it needs an explicit `inline`, or a header included by multiple `.cpp` files will hit a multiple-definition linker error. Stroustrup, *The C++ Programming Language* (4th ed.), class-definition/member-function chapters.
- **Can a `.inl` `#include` go inside the class body?** — the preprocessor doesn't care (pure textual substitution before parsing), but conventional `.inl` content uses out-of-class syntax (`ReturnType ClassName::methodName(...) {...}`), and `ClassName::` qualification isn't valid inside that same class's own body — a compile error, not just a style issue. So the `#include` has to go outside (after) the class definition for the usual `.inl` idiom to work. (If the `.inl` instead used unqualified in-class-style bodies, pasting inside the class body would compile and those definitions would become implicitly inline — but that defeats the purpose of splitting declaration from definition in the first place.) Stroustrup, *The C++ Programming Language* (4th ed.), member-function-definition/qualified-name chapters.
- **Where does `inline` go in the normal `.inl` pattern?** — only on the out-of-class definition in the `.inl` file (`inline void Foo::bar() {...}`), not on the class-body prototype (`void bar();`). It's the definition that needs weak/mergeable linkage for the ODR relaxation to actually work across the many TUs that include the header; the declaration doesn't need to repeat it. Same as the ordinary pattern for any out-of-class inline definition written directly in a header without a separate `.inl`. Stroustrup, *The C++ Programming Language* (4th ed.), inline-function/linkage chapters.
- **Non-inline definitions in a `.inl` don't make `.cpp` files pointless** — a `.inl` can hold a non-`inline` definition, but it's only safe if the owning header is included by exactly one `.cpp` in the whole program (otherwise, same multiple-definition linker error as a non-inline def in a `.h`). `.cpp` files remain essential regardless: (1) their contents compile once into one object file, vs. every including TU re-parsing/re-compiling header/`.inl` content from scratch; (2) they hide implementation details and dependencies from consumers of the header; (3) editing a `.cpp`'s internals only requires recompiling that one file, whereas editing header/`.inl` content forces recompilation of every TU that includes it. Stroustrup, *The C++ Programming Language* (4th ed.), separate-compilation/translation-unit chapters.
- **Header guards / `#pragma once` vs. `inline` — orthogonal problems** — guards prevent a header's content from being pasted more than once into the *same* translation unit (e.g. diamond-shaped includes), a same-TU redefinition problem. `inline` permits the *same* definition to legally exist across *many different* TUs without a linker error, a cross-TU problem. Guard state resets per TU, so it doesn't help across `.cpp` files at all — both mechanisms are needed together on any header with inline definitions: the guard caps it at one copy per TU, `inline` makes many TUs each having one copy legal at link time. A paired `.inl` usually doesn't need its own guard since it's conventionally only included from its one owning header. Stroustrup, *The C++ Programming Language* (4th ed.), preprocessor/header-guard and linkage chapters.
- **`#pragma once` is not an ISO standard feature** — it's a near-universally-supported vendor extension via the general `#pragma` mechanism; the only officially standardized include-guard is the plain `#ifndef`/`#define`/`#endif` macro pattern. Not built in as automatic default behavior from the start because: `#include` is a deliberately dumb, general-purpose text-paste tool (patterns like X-macros rely on including the same file multiple times on purpose); C/C++ favors explicit control over implicit "magic"; the macro-guard idiom already fully solved the problem with existing primitives; and `#pragma once`'s correctness depends on OS/filesystem-level file-identity (symlinks, hard links, case sensitivity, network mounts), which sits awkwardly with a portable, host-independent ISO standard. Stroustrup, *The C++ Programming Language* (4th ed.), preprocessor chapter.
- **What actually contributes to `sizeof(struct/class)`** — only non-static data members (plus alignment padding, and one vtable pointer if the class has any virtual function), never member function code, which lives once in the program's code segment regardless of how many member functions exist. Base class subobjects add their own size on top when inheriting. This is why `FreeStore { FreeStore* next; }` (one pointer member, no virtuals, no bases) has `sizeof(FreeStore) == sizeof(FreeStore*)` exactly, with zero hidden overhead — and why reinterpreting the same raw memory address as `FreeStore*` vs. `Complex*` (via `static_cast`/`reinterpret_cast`, as the IBM tutorial's `MemoryManager::allocate`/`free` do) is purely about which type the *pointer in the code* currently claims, not something the bytes themselves track — the compiler trusts the cast and doesn't verify it, which is why `expandPoolSize` must size every block to the larger of `sizeof(Complex)`/`sizeof(FreeStore*)` to keep both interpretations safely in-bounds. Stroustrup, *The C++ Programming Language* (4th ed.), object-layout/class chapters.
- **`free()` vs `delete` — not interchangeable** — `free()` (C library, `<cstdlib>`) only releases raw memory, no destructor call, and may only be used on memory from `malloc`/`calloc`/`realloc`. `delete` calls the object's destructor first, then deallocates via `operator delete`, and may only be used on memory from a matching `new` expression (`delete[]` specifically for `new[]`). Mixing families (`malloc` + `delete`, or `new` + `free`) is undefined behavior even where `operator new` happens to wrap `malloc` internally, since the standard doesn't guarantee that pairing. `operator new`/`operator delete` are overloadable per-class; `malloc`/`free` are not. `malloc` returns `nullptr` on failure; `new` throws `std::bad_alloc` by default. Stroustrup, *The C++ Programming Language* (4th ed.), free-store/new-and-delete chapter.
- **CMake `file(GLOB ...)` is cached at configure time, not build time** — unlike GNU Make's `$(wildcard ...)` (re-evaluated on every `make` invocation), CMake's `GLOB` scans the directory once during the *configure* step and bakes the resulting file list as a literal list into the generated build files. Adding a new source file later and just running `cmake --build` silently leaves it out — no error, it's just not part of the build — until configure is re-run. CMake 3.12+'s `file(GLOB SOURCES CONFIGURE_DEPENDS ...)` mitigates this by re-checking the glob before each build and auto-reconfiguring if it changed; CMake's own docs call this a developer convenience, not guaranteed bulletproof across all generators. CMake reference documentation, `file()` command.
- **When actual code-substitution inlining helps vs. hurts** — helps for small, hot functions where call overhead (frame setup, jump, return) is comparable to the function's own work, and it can unlock further optimization by exposing the callee's code to the caller's context. Downsides beyond raw binary size: instruction-cache pressure (bloated hot paths stop fitting in the small, fast I-cache, causing more I-cache misses — can make a program *slower* despite removing call overhead, a local win causing a global regression), compile-time cost (the function's body must be visible/recompiled in every including TU), and debugging friction (no clean separate call frame once merged into the caller). In practice, the `inline` keyword is only a hint — modern compilers decide actual substitution via their own cost heuristics largely independent of it, at real optimization levels. Stroustrup, *The C++ Programming Language* (4th ed.), inline-function chapter.
- **`inline` on a function defined and used only within one `.cpp` file does effectively nothing** — no ODR benefit (no other TU ever sees this definition to conflict with), and no meaningful code-substitution effect (the compiler already sees the whole function body in that TU regardless of the keyword, and decides inlining via its own heuristics at real optimization levels either way). The only technically-real effect is a minor linkage nuance (the compiler has slightly more legal room to skip emitting an externally-callable copy) — not something to design around. Stroustrup, *The C++ Programming Language* (4th ed.), inline-function/linkage chapters.
- **Fixing a duplicate global definition: `extern` + one `.cpp`, or an `inline` variable (C++17+)** — a plain `Foo gFoo;` sitting directly in a header (as opposed to a mere declaration) gets separately defined in every TU that includes it — `#pragma once`/header guards don't prevent this, since they only stop re-inclusion *within* one TU, not across different `.cpp` files (see the "orthogonal problems" entry above) — producing a "duplicate symbol" linker error. Two valid fixes: (1) classic — `extern Foo gFoo;` declaration in the header, with the real `Foo gFoo;` definition in exactly one `.cpp` file; (2) C++17 — mark it `inline Foo gFoo;` directly in the header, extending the same ODR-relaxation mechanism `inline` functions have always had to variables, so the linker legally merges the many identical copies into one object (constructor still runs exactly once). Requires actually targeting C++17+ (e.g. `CMAKE_CXX_STANDARD`), not just relying on a compiler's current default. Stroustrup, *The C++ Programming Language* (4th ed.), linkage/inline chapters; cppreference "inline specifier" for the C++17 inline-variable rule.
- **`#define` in headers: legal, but unscoped and not ODR-governed** — macros can live in headers and commonly do (constants, config/feature flags, conditional-compilation guards), but best practice is to give a macro the narrowest scope it actually needs (local to one `.cpp`, `#undef`'d after use if transient), since macros have zero scoping — no namespace, no class scope — a `#define` is visible to everything textually after it until EOF or `#undef`. Multiple-definition rules differ entirely from real language entities: redefining a macro with the *identical* token sequence is explicitly legal (this is why `#ifndef`-style guards work at all); redefining with a *different* sequence without an intervening `#undef` is ill-formed. `#pragma once`/guards only prevent one header from re-defining its own macro twice within one TU — they do nothing to stop two unrelated headers from independently `#define`ing the same name differently, which is a real collision risk unique to macros. Also: macros are pure preprocessor text substitution, fully resolved before real compilation — there's no ODR, no linker symbol, and thus no "duplicate symbol" error possible for a macro the way there is for a global variable. Stroustrup, *The C++ Programming Language* (4th ed.), preprocessor chapter.
- **Industry-standard global constant across files: `inline constexpr`, not a macro** — modern (C++17+) best practice: `inline constexpr int POOLSIZE = 32;` directly in a header. `constexpr` gives a real, typed compile-time constant (usable in array bounds/template args, unlike a macro's blind text substitution); `inline` lets it legally be defined in a header included by many TUs (same mechanism as the `gMemoryManager` fix above). Real scoping and no collision risk, unlike `#define`, and it's visible to debuggers. Pre-C++17 equivalent: `extern const int POOLSIZE;` in the header + `const int POOLSIZE = 32;` in one `.cpp` — works, but the value generally isn't usable in compile-time-constant contexts from other TUs, a limitation that was a big part of the motivation for adding inline variables in C++17. Older `static const` in a header also compiles (each TU gets its own internal-linkage copy, no ODR conflict) but wastes duplicated storage per TU and gives each TU a different address for the "same" constant — legacy idiom, superseded by `inline constexpr`. Stroustrup, *The C++ Programming Language* (4th ed.), constants/linkage chapters; cppreference "constexpr" and "inline specifier."
- **Default arguments belong on the declaration callers see (the header), and only once** — a default value can be specified for a given parameter only *once* across all declarations visible in a TU — repeating it (even with the identical value) on the out-of-class `.cpp` definition is a compile error, stricter than the "identical redefinition is fine" rule for macros or the "redundant but legal" rule for repeating `inline`. It must go on the header declaration specifically, since only TUs that see a declaration with the default attached may omit that argument at the call site — other `.cpp` files never see the `.cpp` definition, only the header. Defaults can be added incrementally across multiple declarations in the same scope for *different* parameters — the restriction is specifically "not the same parameter twice." Stroustrup, *The C++ Programming Language* (4th ed.), function-declaration/default-argument chapter.
- **`static` class data members need a definition too, same as `extern` globals** — `static bool Complex::customAllocator;` written inside a class is only a *declaration*, no storage allocated; it needs exactly one out-of-class definition (`bool Complex::customAllocator = false;` in one `.cpp`) or, since C++17, `static inline bool customAllocator = false;` directly in the class body to skip the separate definition — the same declaration-vs-definition split as the `gMemoryManager` global-variable fix, just applied to a class member instead of a free variable. Omitting the definition compiles fine (declarations don't need bodies) but fails at link time with "undefined symbol" the moment anything actually uses it. Stroustrup, *The C++ Programming Language* (4th ed.), static-member chapter.
- **AddressSanitizer needs `-fsanitize=address` at both compile *and* link** — the compile step instruments memory accesses with calls into ASan's runtime; the link step is what actually pulls that runtime library in. CMake needs both `target_compile_options` and `target_link_options` (3.13+) set to `-fsanitize=address` — compile-only produces "undefined symbols" for the ASan runtime functions, which looks like an unrelated linker bug (not an ARM/M1-specific issue; ASan works fine on Apple Silicon). Also: ASan on a heavy allocation-count workload (millions of `new`/`delete`) can be dramatically slower than typical "2-10x" overhead, since it wraps every allocation with redzone checks and a deferred-free quarantine — a correctness tool, not something to also use for timing/performance measurement. Clang documentation, AddressSanitizer.
- **`std::endl` vs `"\n"`** — `std::endl` inserts a newline *and* forces a flush of the stream buffer; a plain `"\n"` only inserts the character, no forced flush. Whether `std::cout` output appears immediately can depend on buffering mode (often fully-buffered rather than line-buffered when redirected to a file/pipe, vs. a real terminal), so "no output visible yet" isn't reliable evidence a program has hung — it can just mean the buffer hasn't flushed. Useful for isolating that possibility, but forcing a flush and still seeing nothing is real evidence of an actual stuck/slow program, not a buffering illusion. Stroustrup, *The C++ Programming Language* (4th ed.), iostream/stream-buffering chapter.
- **Nulling a pointer after `free`/`delete` is standard, recommended defensive practice** — deallocating doesn't change the pointer *variable*, only the memory it references; without explicitly setting it to `nullptr`, the variable still looks "valid" (non-null) to any later `if`/`while` check, which can cause real bugs like an infinite loop over a linked structure that never terminates. Nulling also makes an accidental double-free harmless, since `delete nullptr`/`free(nullptr)` are explicitly well-defined no-ops. Limitation: it only protects the specific variable reset — any other alias pointing at the same freed address is still dangling. In typical application-level modern C++ this is usually sidestepped via RAII/smart pointers instead; for code working directly with raw pointers by design (like a custom allocator), manual nulling remains standard practice. Stroustrup, *The C++ Programming Language* (4th ed.), pointers/free-store chapter.
- **Why `new` must pair with `delete`, and `malloc` with `free`** — two independent reasons: (1) different allocators keep separate, incompatible bookkeeping (sizes, pool/arena membership, free-list structure); deallocating through the wrong system means it has no record of that address, causing anything from an immediate crash (e.g. "pointer being freed was not allocated") to silent heap corruption; (2) `new`/`delete` additionally run constructors/destructors, which `malloc`/`free` know nothing about — `new` + `free()` skips the destructor (resource leaks even though raw memory is released), `malloc` + `delete` calls a destructor on an object that was never actually constructed (UB). Formally undefined behavior per the standard regardless of whether a particular implementation happens to make it "work" by having `operator new` wrap `malloc` internally — not something a portable program can rely on. A custom allocator handing out pointers into a bulk-`malloc`'d pool (as in this project) is a concrete case where bypassing the matching deallocator would hit exactly this failure. Stroustrup, *The C++ Programming Language* (4th ed.), free-store/new-and-delete chapter.
- **A member function can silently shadow a same-named global function** — unqualified name lookup inside a member function searches inward-out (local scope, then the enclosing class's members) and stops at the *first* match — it never continues out to the global namespace once a name is found in the class. If a class has its own `free(void*)` member, an unqualified `free(x)` call written inside any of that class's member functions resolves to the member, not `::free` from `<cstdlib>`, even though both are plausible candidates — and since the signatures matched here, it compiled cleanly with no warning while silently calling the wrong function. Concrete bug this caused: `MemoryManager::cleanUp()` calling `free(toDelete)` actually called `MemoryManager::free`, which *pushes the node back onto the free list* instead of releasing it — creating an infinite loop that kept reprocessing the same head node forever, unrelated to null-termination or a double-free. Fix: qualify with the global-scope operator, `::free(toDelete);`, to bypass class-member lookup and reach the C library function explicitly. Stroustrup, *The C++ Programming Language* (4th ed.), name-lookup/scope chapter.
- **`#pragma once` is not class-specific** — it guards against pasting a header's content into the *same* translation unit twice, regardless of what the header contains: classes, free functions, variables, macros, all equally. `inline` doesn't substitute for this — `inline` legalizes the *same* definition appearing across *different* TUs; it says nothing about the same definition appearing *twice within one TU*, which is still an error (redefinition) even for `inline`-marked functions. A header that's purely free function definitions (like a global `operator new`/`operator delete` override header) needs `#pragma once`/guards just as much as one full of classes — same "orthogonal problems" split as the header-guards-vs-inline entry above, just as relevant with zero classes involved. Stroustrup, *The C++ Programming Language* (4th ed.), preprocessor/ODR chapters.
- **A parameter/local variable shadows a same-named global — use `::name` to reach the global** — same "innermost scope wins, stop at first match" rule as class-member shadowing, one level shallower: inside a function, plain `foo` always resolves to a parameter or local named `foo` if one exists, completely hiding a global `foo` for that function's entire body. The global-scope resolution operator, `::foo` (prefix, nothing before the `::`), always means "start lookup from the global namespace," bypassing every enclosing/local scope regardless of what's doing the shadowing — same operator as the `::free()` fix, general-purpose for this whole class of shadowing problem. Most style guides sidestep the need for it by convention (e.g. prefixing globals like `gMemoryManager`) rather than relying on `::` routinely. Stroustrup, *The C++ Programming Language* (4th ed.), name-lookup/scope chapter.
- **Global `operator new`/`delete` are "replaceable"** — the global allocation/deallocation functions are explicitly designated by the standard as user-replaceable for the whole program, not restricted to class scope; a class-scoped override (`Complex::operator new`) is a separate, narrower mechanism that only affects that one class. Also: `operator new`/`operator new[]` and `operator new[]`/`operator new` have no required relationship — a program can't rely on the default array form internally calling the default single-object form (implementation-defined at best), so both must be overridden separately to get consistent custom-allocator behavior for both single objects and arrays. Stroustrup, *The C++ Programming Language* (4th ed.), free-store chapter.
- **`operator delete`/`operator delete[]` must be `noexcept` — mismatch is a build error under `-Werror`** — `<new>` declares the global deallocation functions `noexcept` (throwing during stack unwinding, which may already be in progress, would call `std::terminate` anyway); a replacement definition that omits `noexcept` mismatches the standard library's declaration, normally just a warning but a hard error under `-Werror` (`-Wimplicit-exception-spec-mismatch`). `operator new`/`operator new[]` don't need this — they're allowed to throw `std::bad_alloc` by default, so there's no mismatch there. cppreference "noexcept specifier"; Stroustrup, *The C++ Programming Language* (4th ed.), exception-specification chapter.
- **`noexcept`** — a promise that a function will never let an exception escape it; not compiler-verified upfront (code that could throw compiles fine inside a `noexcept` function without complaint) but enforced at runtime — if the promise is broken, the program calls `std::terminate()` immediately, not normal exception propagation to some outer `catch`. Matters beyond documentation: e.g. `std::vector` checks whether a type's move constructor is `noexcept` to decide whether it's safe to use move semantics during reallocation (a throwing move partway through could leave the vector corrupted) vs. falling back to copying — real behavior changes, not just a comment. Destructors are implicitly `noexcept` by default already; explicitly marking deallocation functions `noexcept` makes that same existing expectation explicit at the type level. Also has a conditional form, `noexcept(expr)`, used in template code to propagate a dependent function's exception-safety. Stroustrup, *The C++ Programming Language* (4th ed.), exception-specification chapter; cppreference "noexcept specifier."
- **`std::nothrow` overloads** — `operator new(std::size_t, const std::nothrow_t&) noexcept` / `operator new[](...)`, invoked via `new (std::nothrow) T(...)`, trade C++'s normal exception-based allocation-failure signaling for `malloc`-style behavior: return `nullptr` instead of throwing `std::bad_alloc`. Useful for code avoiding exceptions entirely (embedded/real-time, `-fno-exceptions` builds) while still wanting `new`-expression semantics (proper type, constructor invocation) with a simple null check instead of `try`/`catch`. Yet another independently-replaceable overload — replacing the normal throwing `operator new` doesn't touch this one, same pattern as `operator new` vs `operator new[]`. A matching `operator delete(void*, const std::nothrow_t&) noexcept` also exists, rarely called directly by user code; it's used by compiler-generated cleanup if `new (std::nothrow)` allocates successfully but the constructor then throws, to release the not-fully-constructed memory without a leak. cppreference "operator new,operator new[]," `std::nothrow_t`.
- **Why `new`/`new[]` must NOT be `noexcept` while `delete`/`delete[]` must be** — opposite exception-safety declarations by design, not an arbitrary asymmetry. `new`/`new[]` are declared throwing because `std::bad_alloc` *is* their built-in failure-signaling mechanism (the whole reason the separate `nothrow` overloads exist, for callers who want the alternative). `delete`/`delete[]` are declared `noexcept` because deallocation can happen *during* stack unwinding while another exception is already propagating — C++ can't have two exceptions in flight at once, so a second throw there would just call `std::terminate()` immediately regardless; marking it `noexcept` makes that existing, load-bearing expectation explicit at the type level. Marking `new`/`new[]` `noexcept` mismatches the standard library's own (throwing) declaration and fails to compile, same class of error as leaving `noexcept` off `delete`/`delete[]`, just in the opposite direction. Stroustrup, *The C++ Programming Language* (4th ed.), free-store/exception-specification chapters.
- **`throw(std::bad_alloc)` isn't a separate overload — it's old, removed syntax for the same function** — dynamic exception specifications (`throw(...)`) never participated in overload resolution; a function is distinguished by name + parameter types (and, since C++17, `noexcept`-ness), never by a general `throw(...)` clause. So `operator new[](std::size_t)` and `operator new[](std::size_t) throw(std::bad_alloc)` were always the identical function, even back when that syntax was legal — providing both was always a duplicate-definition error, not two legitimately different things to keep. It also wasn't saying much even when valid: a function with no exception specification is already assumed capable of throwing anything, `std::bad_alloc` included. Dynamic exception specifications were removed entirely in C++17, so this syntax is now also just ill-formed on its own. cppreference "dynamic exception specification (until C++17)."
